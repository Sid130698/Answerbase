Answerbase / Architecture proposal

Answerbase system design.

A permission-aware question-answering service over company documents, designed for a bounded demo with $0 infrastructure spend.

Draft v5 · Self-signup and workspace onboarding 24 November 2026 · Based on PRD v1 · No deployment performed

Unified system architecture

A container-level view of the whole system. Start at the user, follow the request into the API, then follow its labeled request/response connections. The worker connects through the durable database queue. External providers and engineering tooling sit outside the application boundary.

Open full-size architecture diagram ↗ · Boxes represent running components or data stores, not sequential processing steps.

How to read it: the API owns the online request and returns the validated answer to React. Groq is a downstream generation dependency. PostgreSQL unifies retrieval, permissions, and asynchronous job state. The worker reads originals and publishes the chunks that retrieval searches.

Deployment clarification: the API and worker each load the same configured embedding model locally; query reranking runs in the API. This avoids adding a separate model-serving service for v1. They share a VM, but parsing runs in an isolated worker process/container.

Self-signup and workspace access

Users can register themselves. Supabase Auth manages identity verification and sessions. Our existing Spring Boot API creates workspaces and manages membership. There is no separate invitation microservice.

New user → new workspace

  1. The user selects Sign up in React and submits their email to Supabase Auth for a magic link / OTP.
  2. Supabase Auth sends the verification email through a configured SMTP provider. After verification, the browser receives a session and access token.
  3. The user chooses Create workspace. Spring Boot validates the token and verified identity.
  4. The API creates the workspace and its creator’s admin membership in one Postgres transaction. Retry handling prevents duplicate creation.
  5. The new admin can upload documents and ask questions within that workspace. Self-signup never grants access to another workspace.

Joining an existing workspace

An existing admin creates an invitation in the same Spring Boot application. For v1, the UI can expose a copyable invitation link; automatic invitation email can be added without introducing a new service.

Store a hash of a random, expiring, single-use token, the intended email, workspace, and assigned role. The recipient signs up or signs in, then accepts the link. The API verifies the intended email against authenticated identity and activates membership transactionally.

Ownership: Auth stores identities and sessions; our Postgres tables store workspace memberships, groups, roles, document permissions, and invitation state. Spring Boot enforces them on every request.

Public signup is enabled. Apply signup and workspace-creation quotas for the free demo. Existing workspace access still requires an invitation; matching an email domain is not sufficient.

Email delivery is a provider dependency, not another application service. Supabase’s default mail service is for testing and restricts recipients to project-team addresses. Public email signup requires custom SMTP. Provider choice, sending-domain setup, and its cost allowance remain deployment decisions. OAuth signup is an alternative if we want to avoid verification-email delivery for the initial demo.

01Runtime flows

Read each flow top to bottom. Arrows show execution order and the data passed to the next step. Each box names the component that performs the work. Query handling and document ingestion are separate execution paths.

Authentication happens before the first protected request

The React client signs in through Supabase Auth and receives an access token. It sends that token to Spring Boot on protected requests. Spring Security validates the token using the issuer’s signing keys; the API resolves workspace membership and document permissions from PostgreSQL. The auth provider does not sit in the retrieval or generation pipeline.

A · Answer a question

Online request · Spring API orchestrates the pipeline

B · Ingest a document

Upload request followed by an asynchronous worker job

Shared state: ingestion publishes the active document chunks that query retrieval reads. A Postgres job queue connects the API to the worker; the browser does not call the worker. Model execution stays inside the API and worker processes; Groq is an external inference dependency.

Target: a useful, low-traffic public demo at $0 within provider quotas. This is a proposed deployment, not a guarantee of always-on service or the full PRD performance targets.

05Trust is part of the architecture

Evidence and source fidelity

Store document version, section, page, and passage location with every chunk. Preserve PDF coordinates where needed for highlighting. Citation links and original-file access must check current permissions.

Checking that a citation exists does not prove its claim is correct. Measure semantic support in the evaluation suite.

Isolation and deletion

Enforce workspace and document access before retrieval ranking. Apply the same boundaries to source viewers, logs, conversation history, and caches. Deletion removes originals and derived search data.

A privileged database connection must not silently bypass the intended access policy.

Quality gates

Use the PRD’s 60 human-written questions plus 10 adversarial cases. Track retrieval hit rate, correctness, citation support, abstention, and p50/p95 latency.

Publish measured results and gaps. Keep permission and injection tests even if the connector is delayed.

Budget and operational limits

Cap uploads, corpus size, concurrency, context length, and queries per user. Keep ingestion idempotent. On quota exhaustion, show a clear retry state rather than silently selecting a paid provider.

Report actual free-tier spend separately from estimated paid usage cost.

One product decision to resolve

Streaming versus verification: the PRD asks for both fast streaming and checks before returning an answer. Proposed default: send progress immediately, then release a checked complete answer. Sentence-level validation can be evaluated later. Measure time to first verified content separately from time to first progress event.

06Scope and next decisions

First working slice

Two workspaces, a small public corpus, PDF/DOCX/Markdown upload, asynchronous indexing, cited Q&A, source viewing, feedback, and an initial evaluation baseline.

Then add hybrid-search tuning, reranking experiments, the admin usage view, and one connector. OCR stays a stretch goal.

Decisions still open

  • Accept VM administration and verify Oracle capacity.
  • Select generation and embedding models through evaluation.
  • Set demo corpus and user quotas after measuring storage.
  • Choose the licensed public corpus and single connector.
  • Validate the PRD’s 50,000-chunk target independently of the small free demo.
