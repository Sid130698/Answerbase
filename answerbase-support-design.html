One company boundary.
Two independent applications.

Clients work within their own organization. Answerbase employees use a separately deployed staff application to inspect and repair issues, while the real customer application runs inside an isolated frame with the selected user’s actual permissions.

Unified architecture

Solid arrows show the direction of requests or credential delivery. Database operations read and write; responses return to the caller along the same connection. The customer app inside the frame is the real, independently built app—not a duplicate support implementation.

The database rejects staff/customer identity overlap and cross-company memberships. No membership row means no workspace access. Staff status is not a role on a client organization.

Support-session lifecycle

  1. Staff signs in using a dedicated, explicitly provisioned account. The API verifies active staff access.
  2. Staff selects a client and supplies a ticket reference or reason. The backend creates a 30-minute session bound to that employee and company.
  3. Selecting a user issues a random 10-minute grant, capped by session expiry. Only its SHA-256 hash is stored. Previous grants for that session are revoked.
  4. The parent sends the grant to the customer frame through exact-origin/source-validated messages. No tokens appear in URLs, audit logs, or persistent customer storage.
  5. The delegated API resolves the real employee and target account and calls the existing customer authorization services. Successful operations and audit events commit together.
  6. Staff repairs use separate endpoints, retain organization constraints and last-admin rules, and record the before/after role.
  7. Ending a session, expiry, or disabling the employee prevents subsequent delegated requests. Closing a browser tab alone is not proof of logout; server-side expiry remains authoritative.

This reproduces account permissions and server-side state. It does not reproduce the customer’s extensions, device, unsaved form inputs, or exact browser session.

Independent deployment and future SSO

The two frontends have independent packages, lockfiles, Docker images, CI jobs, origins and browser authentication storage. They share an API deployment today through separate customer, staff and delegated route groups. The support frontend can move to another server without rebuilding the customer UI except when its trusted support origin changes.

Authentication, organization enrollment, workspace authorization and support delegation remain separate responsibilities. Future SSO connections, verified domains, or company.answerbase.com routing must resolve identities and verified company enrollment; the URL itself never authorizes access.

Implemented scope and limitations

Organization creation, workspace creation/switching, membership diagnostics and repairs, delegated customer view, staff login gating, expiry/revocation and audit records are the current slice. Document uploads, question answering, production SSO/domain enrollment, customer invitation approval UI, staff provisioning UI and browser/device reproduction are not implemented.

Staff provisioning is a trusted local developer command. The support UI shows customer UUIDs because a customer email/profile directory is not yet stored. Append-only audit triggers protect normal writes; a privileged database owner can change database controls, so this is not an external tamper-proof audit archive.
